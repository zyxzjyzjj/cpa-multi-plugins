# Issue #12 / #13 核查

核查基线：`2fcaee8`（含上游 v0.12.85 的可选首包门和 Trae 的请求指纹诊断）。以下结论基于源码、CPA v7.3.4 宿主实现及本地模拟上游测试；没有用真实 Trae/WorkBuddy/Qoder 账号调用远端服务。

## #12：流式错误丢失状态

原报告：[issue #12](https://github.com/mmqz/cpa-multi-plugins/issues/12)。问题真实，但当前基线已经带有部分修复：WorkBuddy / Qoder 的 `stream_head_timeout` 首包检测门默认是 0，未配置时仍立即返回成功。Qoder 的同步聚合错误也刻意没有实现 `StatusCode()`。

本次处理：

- 两个 provider 默认启用 30 秒检测窗口，并在管理配置中显示该参数；显式设 0 可关闭。
- 窗口内的上游 HTTP / 帧内错误在回答前通过失败 RPC 返回，保留 HTTP 状态，不先发 role 开场帧。未知 WorkBuddy 错误用 502，输入过长用 413，模型未注册用 422。
- 请求构造、签名及上游连接失败不再返回一个成功空流。
- Qoder 同步聚合路径保留帧内原有状态；无法识别时用 502。
- WorkBuddy 工具调用 delta 计为真实回答，避免后续失败吞掉已经生成的工具调用。
- 已经交付回答后的错误继续走流内通知。30 秒检测窗口届满后保留原来的交付策略；可提高窗口以适配较慢的上游。

保留的既有策略：WorkBuddy 6004 属于单模型限流，继续由 `(uid, model)` 冷却表管理，不伪装为整账号额度耗尽；也没有修改 429 的账号删除/禁用策略。

回归测试覆盖回答前失败不发任何帧、回答后失败保留回答、工具调用、窗口期限、显式禁用、状态码映射，以及 Qoder 同步路径。

## #13：SOLO 非流式 4001

原报告：[issue #13](https://github.com/mmqz/cpa-multi-plugins/issues/13)。当前代码两条路径都调用同一个 `PrepareBody`，都强制上游 `stream=true`。不能仅凭原报告就断言当前版本所有非流式请求必然失败。

确认的缺陷是两条执行路径都忽略 `ExecutorRequest.Model`，直接使用 `Payload.model`。CPA 宿主把解析别名后的模型放在 `Model`，同格式请求不一定改写 body，因此上游可能收到客户端别名或默认模型，产生 4001。

本次让同步和流式入口共用模型归一化逻辑，优先使用宿主已解析的模型名，再由 `PrepareBody` 剥离 `-solo` 等命名空间。通过本地 HTTP 上游实际调用两个执行入口，验证别名请求均成功且最终请求逐字节相同。无效 JSON 作为请求级 400 返回。

4001 的附带状态问题也确认存在：旧 `soloFaultStatus` 返回 404，但随后被 `upstreamStatusError` 丢掉；注释声称“404 不长冷却”不准确。本次参数/模型不匹配改为 422，输入过长保留 413，未知上游故障保留 5xx，并验证最终 RPC 信封的状态。422 是请求级终止，不承诺跨 provider 重试。

真实上游的历史“仅改变 stream 就必挂”现象仍需使用相同账号、模型及请求在部署环境复验。本次修复覆盖已证实的模型路由缺陷和状态丢失，保留已有 `TRAE_DEBUG_PAYLOAD=1` 指纹诊断能力。
